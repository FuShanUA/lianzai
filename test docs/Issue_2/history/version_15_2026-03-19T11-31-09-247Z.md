# 《数据认责体系建设白皮书》连载二：谁才是真正的数据主人？ 厘清数据认责的核心角色与概念边界

在上一期内容中，我们探讨了“十五五”规划背景下，政企数据治理正全面迈入深水区。企业要想真正释放数据要素的价值，顺利通过DCMM贯标并让数据资产入表，就必须完成从“纸上制度”到“业务日常”的跨越。而实现这一跨越的基石，正是建立一套行之有效的数据认责体系。 

但在着手搭建体系之前，绝大多数企业都会被一个看似简单却极易引发部门扯皮的问题绊倒：**到底谁才是数据的主人？**

今天，我们将回归业务本源，为您拆解数据认责体系中的核心角色，并厘清那些在日常沟通中极易混淆的关键概念。

### **谁在为数据负责？核心角色全景图**

在国际经典的数据管理理论与国内政企的落地实践中，数据认责体系通常由几个关键角色构成。准确理解这些角色的定位，是终结部门推诿的第一步。

**数据主人（Data Owner）**。组织内对特定数据集负有最终责任的部门或个人，对数据的定义、使用、存储和维护负有最终的决策权和责任。

**数据管理专员（Data Steward）**。也称数据管家，代表组织管理数据资产，确保数据需求方者获得高质量数据，以及数据得到有效地应用，使组织得到最大利益。

**数据保管人（Data Custodian）**。负责数据的技术性保管与运行维护，包括数据的存储、传输与安全控制，保障数据技术环境的稳定性。

### **概念辨析：别把问责当职责，把管理授权当法律确权**

在明确了角色之后，我们还需要扫清认知上的障碍。在实际推进数据治理时，高管和业务负责人常常会混淆两组核心概念。

**第一组：问责（Accountability）与职责（Responsibility）**。这是数据认责中最核心、也最容易被忽视的区别。 在数据认责的RACI模型中，严格区分问责（Accountability）与职责（Responsibility）不仅是概念辨析的要求，更是正确梳理认责和构建有效治理体系的前提。**Accountability（当责/问责）聚焦于“对结果负责”**，它代表的是一种承诺与最终的决策权。相比之下，**Responsibility（职责/执行）则聚焦于“对过程负责”或“对任务负责”**，它关注的是具体动作的执行与交付。

**第二组：数据认责与数据确权**。随着“数据二十条”的发布，数据确权成为了热门话题。很多企业误以为，做数据认责就是要在法律层面搞清楚数据归谁所有。 事实上，**数据确权通常指法律层面的所有权确认**，解决数据要素在外部场景的数据权属与权益边界问题，具有法律和宏观市场属性。相比之下，**数据认责聚焦于组织内部的管理授权与责任承担**，关注组织基于对其持有数据如何由具体的部门、岗位和人员有效管理，侧重于运营效率与风险控制。

### **直击痛点：业务部门为何总觉得在给IT打工？**

理清了概念，我们再来看看现实。在很多政企机构中，数据认责往往沦为信息技术部门的“摊派任务”。数据管理部门发出一堆Excel表格要求业务部门认领数据，业务人员则满腹牢骚，认为自己是在帮IT干活。

这种现象的根源在于结构性的错位与权责利的不对等。

数据与业务流程紧密伴生。当一线业务人员面临“业务推进速度”与“数据录入质量”的冲突时，比如为了赶在月底前完成签单指标，他们本能地会选择牺牲数据质量，随意填写客户信息。此时，**如果缺乏独立的认责机制，IT部门试图强行规范数据，就会面临“不懂业务含义、无权干涉流程”的尴尬境地**。

最终的局面往往演变成：管数据的人（IT）不懂业务，懂业务的人（业务部门）不管数据。业务部门产生了严重的依赖心理，将本应承担的源头治理责任全部推卸给技术团队。这种脱离业务本源的治理，注定会演变成一场形式主义的消耗战。
