# 《数据认责体系建设白皮书》连载二：谁才是真正的数据主人？ 厘清数据认责的核心角色与概念边界

在上一期内容中，我们探讨了“十五五”规划背景下，政企数据治理正全面迈入深水区。企业要想真正释放数据要素的价值，顺利通过DCMM贯标并让数据资产入表，就必须完成从“纸上制度”到“业务日常”的跨越。而实现这一跨越的基石，正是建立一套行之有效的数据认责体系。

但在着手搭建体系之前，绝大多数企业都会被一个看似简单却极易引发部门扯皮的问题绊倒：**到底谁才是数据的主人？**

今天，我们将回归业务本源，为您拆解数据认责体系中的核心角色，并厘清那些在日常沟通中极易混淆的关键概念。

### 谁在为数据负责？核心角色全景图

在国际经典的数据管理理论与国内政企的落地实践中，数据认责体系通常由几个关键角色构成。准确理解这些角色的定位，是终结部门推诿的第一步。

**数据主人（Data Owner）**
这是拥有数据资产最高裁决权和最终解释权的角色。数据主人对特定数据的定义、质量标准和安全合规承担最终的领导责任。在实际业务中，这个角色通常由产生数据或对数据拥有最终解释权的业务部门负责人担任。数据主人未必亲自下场清洗数据，但他们拥有决定数据该如何被管理的“拍板权”。

**数据管理专员（Data Steward）**
如果说数据主人是决策者，那么数据管理专员就是具体的执行者与协调者。他们也被称为“数据认责人”或“数据管家”，负责将高层的治理策略转化为日常的业务规则定义、标准维护以及质量监控动作。这个角色需要深厚的业务背景，是连接业务需求与IT技术之间的桥梁。

**数据保管人（Data Custodian）**
这是技术侧的守护者。数据保管人通常由IT运维、数据库管理员或安全专家担任，负责数据的物理存储、系统运行维护、加密传输与访问权限控制。他们确保数据在技术环境中的稳定与安全。

### 概念辨析：别把管理授权等同于法律确权

在明确了角色之后，我们还需要扫清认知上的障碍。在实际推进数据治理时，高管和业务负责人常常会混淆两组核心概念。

**第一组：数据认责与数据确权**
随着“数据二十条”的发布，数据确权成为了热门话题。很多企业误以为，做数据认责就是要在法律层面搞清楚数据归谁所有。
事实上，数据确权解决的是数据在跨组织流通、交易时的法律权属与收益分配问题，具有宏观市场属性。而数据认责聚焦于组织内部的管理授权，它关注的是企业内部哪个部门、哪个岗位应该把这批数据管好。
两者相互依存。外部的资产化确权压力，会倒逼企业内部把责任落实到人；而内部一个认责到位的治理体系，能够提供清晰的数据血缘和操作记录，大幅降低企业在外部确权时的合规自证成本。

**第二组：问责（Accountability）与职责（Responsibility）**
这是数据认责中最核心、也最容易被忽视的区别。
问责（Accountability）聚焦于“对结果负责”，具有唯一性和不可转授性。它通常落在拥有预算权和决策权的业务高管肩上。
职责（Responsibility）聚焦于“对过程负责”，关注具体任务的执行，通常由一线业务人员或IT工程师承担。
举个真实的业务场景：如果因为系统漏洞导致核心客户数据泄露，IT工程师没有尽到安全防护的“职责”；但营销总经理作为客户数据的“数据主人”，依然要面对董事会或监管机构的“问责”，因为他承担着监管不力或资源投入不足的最终管理责任。严格区分这两者，才能真正做到“问责有主，执行有力”。

### 直击痛点：业务部门为何总觉得在给IT打工？

理清了概念，我们再来看看现实。在很多政企机构中，数据认责往往沦为信息技术部门的“摊派任务”。IT部门发出一堆Excel表格要求业务部门认领数据，业务人员则满腹牢骚，认为自己是在帮IT干活。

这种现象的根源在于结构性的错位与权责利的不对等。

数据与业务流程紧密伴生。当一线业务人员面临“业务推进速度”与“数据录入质量”的冲突时，比如为了赶在月底前完成签单指标，他们本能地会选择牺牲数据质量，随意填写客户信息。此时，如果缺乏独立的认责机制，IT部门试图强行规范数据，就会面临“不懂业务含义、无权干涉流程”的尴尬境地。

最终的局面往往演变成：管数据的人（IT）不懂业务，懂业务的人（业务部门）不管数据。业务部门产生了严重的依赖心理，将本应承担的源头治理责任全部推卸给技术团队。这种脱离业务本源的治理，注定会演变成一场形式主义的消耗战。

### 破局关键：RACI模型初探

要打破这种“业务缺位、技术背锅”的僵局，我们需要一套科学的工具，将抽象的治理理念转化为具体的行动指南。这就是RACI责任分配矩阵。

RACI模型将参与数据管理的各方划分为四个维度：
*   **A（Accountable）当责者**：对应数据主人，对结果负全责，且针对单一数据项必须唯一。
*   **R（Responsible）执行者**：对应数据管理专员或具体操作岗，负责执行具体的质量检核与维护动作。
*   **C（Consulted）咨询者**：在制定规则或修复问题时需要提供专业意见的专家，如架构师或分析师。
*   **I（Informed）知情者**：数据变更后需要被通知的下游使用方。

通过构建RACI矩阵，企业可以将庞杂的数据资产与具体的组织架构、岗位人员精准映射。但问题随之而来：如果矩阵的粒度太粗，责任依然无法落实到人；如果粒度太细，要求对每一个字段都明确唯一责任人，巨大的工作量又会瞬间压垮整个组织。
